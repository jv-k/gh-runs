# Settings

> Terms are defined in [CONTEXT.md](../../CONTEXT.md). Decisions are recorded in [adr/](../../adr/).

## Purpose

Settings **expose intent, never mechanism**. A setting earns its place only if a person can answer it from their own context. A question that requires the token tier, the points model and the repo count to answer belongs to the scheduler, which has all three, and not to the user, who has none.

## Requirements

**R1.** Settings MUST live in a single config file at `$XDG_CONFIG_HOME/gh-runs/config.yml`, defaulting to `~/.config/gh-runs/config.yml`. On Windows, where `$XDG_CONFIG_HOME` is unset, the fallback MUST be `$AppData/gh-runs/config.yml`, mirroring gh's own verified precedence (Constraints).

**R2.** Machine-local data MUST NOT be written into the config file. The local-store (persisted ETags, discovered repositories, window state) lives under the XDG cache directory, and the deletion log under the XDG state directory, per [ADR-0017](../../adr/0017-the-local-store-on-disk-contract.md). A person MUST be able to copy their config file to another machine, or commit it to a dotfiles repository, without carrying machine-local state with it.

**R3.** Every key MUST be optional. A missing config file, and an empty one, MUST both be valid and MUST produce identical behaviour to a file containing every default.

**R4.** Precedence MUST be flags, then environment, then config file, then defaults (highest first).

**R5.** The keybinding profile MUST offer **exactly two** values: **Vim** and **Standard**. A third profile MUST NOT be added on the grounds of platform.

**R6.** A theme setting MUST exist, offering an **auto** member that derives its palette from the terminal background (as gh does), plus explicit **dark** and **light**, and defaulting to auto. A member joins the set if and only if it clears R22's floors against the background it paints, and nothing else bounds the set: the bound is a property a test enforces rather than a count a reviewer holds. `NO_COLOR` overrides every member (R15).

**Auto is the only member that does not paint.** `auto` inherits the terminal's background and resolves dark or light from it. Every other member carries its own background and the tool paints it, by cell fill, so every cell on screen is one the tool set. That is what makes R22 exact arithmetic for those members rather than an assumption about somebody's terminal, and [ADR-0025](../../adr/0025-named-themes-and-who-owns-the-background.md) carries the reasoning, the mechanism and the six options it beat.

**The painting and the named members arrive in 2.1, and 2.0.0 ships the three members above unpainted.** This requirement describes the set the setting reaches at 2.1: `auto`, `dark`, `light`, `nord`, `dracula`, `gruvbox-dark` and `solarized-light`. A named member is a borrowed identity adapted to R22's floor rather than a byte-faithful copy of the theme it names, which ADR-0025 states in its own voice because it is the part an operator can check.

**R7.** Repositories MUST be excludable and pinnable by host-qualified identity. Exclusion MUST remove a repository from discovery, the Feed and all polling. Pinning MUST prioritise it. Where a repository is both excluded and pinned, **exclusion wins**: it is removed from discovery, the Feed and all polling, and the pin has no effect. Exclusion is the stronger signal, and honouring the pin would poll a repository the person told the tool to leave alone, at a direct rate cost ([ADR-0003](../../adr/0003-multi-repo-via-client-side-fanout.md)).

**Both halves ship in 2.0.0. "Prioritise" means a cadence promotion** (issue [#97](https://github.com/jv-k/gh-runs/issues/97)). A pinned repository is promoted to the scheduler's medium tier, which is the cadence a repository on screen already gets, and it holds that cadence while scrolled away. That is the reading [ADR-0021](../../adr/0021-the-scheduler-cadence-policy.md) makes natural: the viewport promotes by scroll position, and a pin says the same thing persistently rather than by where the operator happens to be looking.

**The pin key shipped after its subsystem rather than ahead of it.** It was deliberately absent while nothing consumed it for order, because cadence comes from the tier policy and the Feed orders rows by start time, so a `pin` key would have configured nothing observable. That is R11's ruling, the do-nothing switch [notifications](../notifications/requirements.md) R13 refuses, and nothing forced the key in early: config keys are optional (R3), an unknown key only warns (R14), and adding it once the tier policy took the input needed no migration.

**The promotion is bounded by the secondary ceiling, which is what makes it affordable.** ADR-0021 chose the viewport rule partly because its cost is capped by terminal height rather than by poll-set size, and an operator-authored pin list is unbounded, so a naive promotion would reintroduce the cliff that reading was picked to avoid. The medium tier's interval is therefore auto-scaled against the same ~900 points/min ceiling the ambient tier is already scaled against, rather than against a fresh constant, and it is priced against the headroom that tier leaves so the bound is on the whole schedule rather than on one tier's share. The list may be any length and the schedule's cost cannot pass the ceiling. The promotion also never inverts: a pinned repository is never polled less often than an unpinned one. ADR-0021 carries the arithmetic.

**R7 names three surfaces, and no fourth.** Exclusion removes a repository from discovery, the Feed and all polling, and reaches no further. It leaves alone a repository the operator names in the present tense: `-R`, `GH_REPO`, and the working directory that R4's precedence and [cli-surface](../cli-surface/requirements.md) R22's MUST both resolve to "that repository". Refusing those would invert R4, which puts flags and environment above the config file, and would leave no path to a repository whose only sin is being noisy, which is the same property that makes it a Purge target.

**R8.** The share of the API **Budget** this tool may spend **polling** MUST be settable, expressed as a share of the person's primary rate allowance and nothing else. It MUST NOT be expressed as an interval, a request rate, or a delete rate. The polling scheduler derives its intervals from it.

**The word "polling" is load-bearing and MUST NOT be dropped.** The Budget is a share of the **primary** limit, which is what reads spend. A Purge's writes are bound by the **secondary** limit, so this setting never throttles one, and [rate-governor](../rate-governor/requirements.md) R19 forbids letting it. A label promising a share of everything would be a lie in the one case a user would most notice: setting 25% and finding their Purge still runs at full rate.

**R9.** The filter applied to the Feed at launch MUST be settable, and MUST be stored as the structured Filter ([ADR-0016](../../adr/0016-the-filter-representation.md)) with Status and Conclusion as distinct typed fields, not as the CLI's permissive `-s/--status` string, whose conflation of the two is a poor thing to persist. This spelling is what the note under R19 calls the Runs tab's this-repo scope by another name, and the note below records the one thing it still needs before it is that.

**R9 ships all nine of ADR-0016's axes** (issue [#102](https://github.com/jv-k/gh-runs/issues/102)). The file spells branch, commit, actor, event, workflow and created, plus status and conclusion as two keys, which is the distinction this requirement is about and the whole of what it demands, plus `repos` as a sequence whose entries are `OWNER/REPO` or the `this-repo` marker the note below decides.

The repository axis was the one omission, and it was out under R17 rather than by ADR-0016's choice: R17 makes the view and the file the same settings, the view edits this filter in the grammar `filter` owns, and that grammar carried no repository token, so a stored key would have been a setting the view could neither show nor edit. ADR-0016 leaned the other way throughout, naming "the Feed's filter input" as the consumer that needs the axis, and #102 resolved the disagreement in the ADR's direction by giving the grammar a `repo:OWNER/REPO` token. The key, the Settings row and the Feed's input are now one spelling, and the view needs no code of its own to edit it.

**A named repository is not the working directory's repository, and the `repos` key spells both** (issue [#117](https://github.com/jv-k/gh-runs/issues/117)). R1 and R2 make this file a single directory-independent document, so a pinned name does not follow the operator between directories, which is what the note under R19 means by the Runs tab's this-repo scope. The key therefore takes `this-repo` as an entry beside any `OWNER/REPO` entries, the same word `workflows_scope` and `storage_scope` use, and the Feed resolves it to the working directory's repository per launch. The entry is an OR member like any other: `repos: [this-repo, cli/cli]` matches either.

**The stored value is never the resolved one, and that is what keeps R17 honest.** The Settings view seeds its edit buffer from the launch filter and saves through the same grammar, so a value resolved before it reached this file would come back as a plain repository name written over the marker, by the first save the operator makes in whatever directory they happen to be in. That is the R17 defect that kept the repository axis out of the file to begin with. `this-repo` survives the round trip because nothing on the path from the file to the view resolves it: [ADR-0016](../../adr/0016-the-filter-representation.md) puts resolution at the Feed's match, against the same working-directory resolver R19's two scopes already use.

The `exclude` and `pin` keys do not take `this-repo`. They are R7's, and nobody has decided they should.

**R10.** Timestamps MUST be switchable between relative and absolute, and MUST default to **absolute**. [live-run-feed](../live-run-feed/requirements.md) R4a sizes the `run_started_at` column to the absolute instant as its reference rendering and makes the relative form "narrower, never wider", so absolute is the shape the column is built around and relative is the opt-in.

**R11.** Notification events MUST be selectable as a **flat list of per-event options** in the Settings menu, one option per event in [notifications](../notifications/requirements.md) R4's table. They MUST NOT be arranged as a grid of events against scope, or of events against Conclusion. Each option MUST be expressed at the level of intent: a person deciding whether to turn one on MUST be able to answer from their own context, without knowing which endpoint or event name produces it. The default MUST be conservative, and R4's table is where it is fixed.

**R11 is deferred to 2.1 with [notifications](../notifications/requirements.md), and the entries defer with the feature rather than shipping inert.** R11 renders R4's events, and R4 defers to 2.1 ([PRD](../../PRD.md) Scope, [ADR-0013](../../adr/0013-dependency-pins.md)). So the 2.0.0 Settings menu carries no notification options, because a toggle with no subsystem behind it is the do-nothing switch [notifications](../notifications/requirements.md) R13 refuses ("rather than offering switches that do nothing") and R18's golden asserts the view never renders. Nothing forces the keys in early: config keys are optional (R3), an unknown key only warns (R14), and 2.1 adds them without a migration. R11 activates when the feature it configures ships.

**R12.** The threshold above which a destructive action requires the operator to **type the affected count** MUST be settable, MUST default to **50**, and MUST be bounded by a hard maximum of **500** that the config cannot exceed. Note the inversion: raising the threshold *lowers* protection, so the floor under protection is implemented as an **upper bound on the setting's value**. A value above the maximum MUST be clamped with a diagnostic, not honoured. There MUST be no lower bound. A person may demand the typed confirmation for every deletion.

**Neither number is settable past the clamp, and that is R13's test applied rather than an exception to it.** The threshold is intent: "how many deletions do I want to have to think about" is answerable from a person's own context. The maximum is not, and it is not offered. [purge](../purge/requirements.md) R7 and R8 carry the reasoning for both numbers and its open question 1 records it. The short of it: 50 is roughly where a frozen set stops being reviewable by eye, and 500 sits three orders of magnitude below the reference repository's ~28,700 Runs, so a real Purge types its count whatever this key says.

**R13.** The following MUST NOT exist as settings, in the config file, as flags, or as environment variables. They are absent, not hidden.

| Rejected | Reason |
|---|---|
| The scheduler's poll interval in seconds | Mechanism. Choosing it needs the token tier, the repo count and the points model. The scheduler has all three, the user has none. The discovery refresh interval (R20) is not this key: [ADR-0020](../../adr/0020-discovery-scope-adoption-and-refresh.md)'s two-tier re-probe makes it cheap by construction, so it passes the intent test this row fails |
| Deletes per second | Mechanism, and dangerous. The adaptive governor beats any fixed number. This knob's only real function is letting someone get their account blocked |
| Cache TTL | Meaningless. ETag revalidation is already free *and* correct, and a TTL could only make data staler |
| Concurrency | Internal. Bounded by the secondary rate limit, not by taste |
| A stored setting that skips confirmation | The one thing standing between a keystroke and 5,000 deleted Runs. The CLI's `--yes` is not this and is not affected: a mandatory per-invocation flag *is* that surface's confirmation ([cli-surface](../cli-surface/requirements.md) R11), where a persistent setting could only waive one. What is rejected here is the stored form, including any key that would supply `--yes` on the operator's behalf |

**R14.** An unrecognised config key MUST produce a diagnostic and MUST NOT fail the run. Each of R13's five rejected keys MUST produce a **specific** diagnostic naming its reason from that table, rather than a generic "unknown key". The point of R13 is that these are refused for stated reasons, and someone who reaches for one deserves the reason rather than silence.

**R15.** `NO_COLOR`, set to any value, MUST suppress ANSI colour output, and MUST override the theme setting (R6) rather than be overridden by it. Accessibility is not a preference to be configured away.

**R15a.** The colour profile MUST be resolved by this tool and handed to Bubble Tea explicitly through `tea.WithColorProfile`. It MUST NOT be left to `colorprofile.Detect`, which resolves this differently and resolves it against R15. The order is:

1. **`NO_COLOR` present at any value, including empty: cap the profile at `Ascii`.** Nothing below this line may raise it, and the output being piped MUST NOT waive it.
2. Else `CLICOLOR_FORCE` set to a non-zero value: keep colour even where the output is not a terminal.
3. Else `CLICOLOR=0`: cap at `Ascii`.
4. Else detect.

"Cap" is the operative word, and it is never "set". A profile already lower stays lower: `NO_COLOR` on a piped stream leaves `NoTTY` alone rather than promoting it to `Ascii`.

**The pinned library has already decided this, and it decided the other way.** [ADR-0013](../../adr/0013-dependency-pins.md) carries the measurement. In short, `colorprofile` v0.4.3 reads `NO_COLOR` through `strconv.ParseBool`, so `NO_COLOR=yes` and `NO_COLOR=` do not suppress and `NO_COLOR=0` does not either. It gates that test on the output being a terminal while leaving `CLICOLOR_FORCE` ungated, so a **piped** `NO_COLOR=1` with `CLICOLOR_FORCE=1` renders full truecolour. And `CLICOLOR=0` is inert there, because its `CLICOLOR` limb only ever raises a profile. Three specifications disagree about `NO_COLOR` and the library follows none of them: no-color.org says present and **not** empty, gh 2.92.0 says **any** value, `ParseBool` accepts eleven spellings and rejects `yes`. R15 follows gh deliberately and this requirement is what makes that true rather than aspirational. Four lines of resolution beat a detection that is wrong in five measured cases.

**R15b.** The tool MUST honour gh's accessibility configuration where set: `GH_ACCESSIBLE_COLORS` / `accessible_colors` (4-bit palettes chosen against the terminal background), `GH_ACCESSIBLE_PROMPTER` / `accessible_prompter` (prompts compatible with speech synthesis and braille displays), and `GH_SPINNER_DISABLED` / `spinner disabled` (text progress in place of motion). [ADR-0008](../../adr/0008-full-cli-surface-despite-gh-overlap.md) commits to gh's flags and not its config, so this is a decision rather than an inheritance, made on the same reasoning as R15's trio: someone who configured these for gh is holding a gh extension, and accessibility is where honouring is the right default. The spinner setting is load-bearing rather than cosmetic, because a Purge shows progress for ~155 minutes in the normal case and as long as ~10 hours at the throttle's floor.

**R16.** Meaning MUST NEVER be encoded in colour alone. Every Status, Conclusion and outcome distinction the interface draws MUST survive being rendered in monochrome, carrying a **text** label that is not redundant with its colour.

**A glyph is not a text label, and this requirement used to permit one.** AC10 tests distinguishability "by text alone", so an implementer taking R16's offer of a glyph fails AC10, and the two could not both be met. Text wins on three counts. AC10 is the test and it already said so. [log-viewer](../log-viewer/requirements.md) R9 states the same rule for log content with no glyph limb, so the canon was two-to-one against it already. And a glyph is exactly what a terminal with the wrong font drops, which makes it the one fallback that shares a failure mode with the thing it is a fallback for. v1's `SKIP`/`GOOD`/`FAIL` were text.

**R17.** The TUI's Settings view and the config file MUST be the same settings. A change made in the view MUST persist to the file, and MUST NOT discard comments, key order, or keys the running version does not recognise. The config file is read at startup and is not watched while running: the view is the authority for a running instance and writes its changes back, and a hand-edit to `config.yml` made outside the tool is picked up at the next launch. Watching the file would race an external edit against the view's own writes for a rare case, and is deferred.

**R18.** The Settings view MUST render to a frame from held state alone, with no live terminal and no network, and that frame MUST be verified by golden-file tests. One of those goldens MUST assert that none of R13's rejected settings appears in the rendered view. R13's claim is that they are absent, not hidden, and absence is the one claim prose cannot keep: a view built by walking a schema grows a row the moment someone adds a key, and R14's diagnostic fires on a key that was *typed*, never on one this view offers. No other requirement here would catch it.

**R19.** The Workflows and Storage tabs MUST each carry an **independent scope**, settable to `all-repos` or `this-repo`, and both MUST default to `all-repos`. They MUST be settable separately, so that scoping one tab leaves the other alone. `this-repo` MUST resolve to the repository of the working directory. Where there is no such repository, the tab MUST fall back to `all-repos` and MUST say so, rather than paint an empty view or interrupt with a picker. This is intent-level under R13's test: "do I want to see every repository, or the one I am in" is answerable from the person's own context, unlike a fan-out cost.

**The Runs tab gets no scope setting of its own, and the honest reason is narrower than it first appears.** [live-run-feed](../live-run-feed/requirements.md) **R1 and R2** and that document's Purpose line are what fix the Feed cross-repository: the Feed is the launch view and spans every repository on the account. R3 is a different requirement and says something more specific. It forbids per-repository **navigation** (no tabs, no sections, because ~26 tabs is not navigable) and mandates a repository **column and filter**. An earlier wording here cited R3 as the thing that "fixes it cross-repository", which it does not.

**And R3's filter, plus R9's settable launch filter, are what a persistent this-repo scope would be made of.** A launch filter pinned to the working directory's repository would give the Runs tab what R19 gives the other two, reached through the filter rather than through a scope key. So the distinction R19 draws is about **mechanism, not capability**: the Feed would express scope as a filter it already has, and the other two tabs have no filter to express it through. What R19 must not claim is that the Runs tab can have no equivalent. It can have one, spelled differently.

**Both halves are decided, and the equivalence is `repo:this-repo`** (issues [#102](https://github.com/jv-k/gh-runs/issues/102) and [#117](https://github.com/jv-k/gh-runs/issues/117)). #102 gave the filter input's grammar and the launch filter a `repo:OWNER/REPO` token, which states a **named** pin. #117 gave the same grammar `repo:this-repo`, which states the pin this note describes: it resolves to the repository of the working directory, per launch, exactly as this requirement's two scopes do and against the same resolver. An earlier wording here said the Runs tab "has one", present tense, where no built surface could state it. It has one now, spelled as a filter token because that is the mechanism the Feed has and the other two tabs do not.

**The fallback obligation travels with the capability.** This requirement's letter binds the Workflows and Storage tabs, because they are the tabs a scope key exists for. The rule it states is about the working directory resolving to nothing, and that happens to the Runs tab's pin identically. So where `repo:this-repo` resolves to no repository, the token contributes nothing, the Feed shows every repository, and the Feed MUST say so in the filter chrome, immediately beneath the line that states its active filter, rather than paint an empty view or interrupt with a picker. A clause on that line itself was tried and does not fit inside [live-run-feed](../live-run-feed/requirements.md) R4a's 100 columns ([ADR-0016](../../adr/0016-the-filter-representation.md)'s amendment). [live-run-feed](../live-run-feed/requirements.md) R3 carries it on that side.

**R20.** The discovery revalidation interval MUST be settable as `discovery_refresh_minutes`, MUST default to **5**, and MUST be bounded by a floor of **1** that the config cannot go under. A value below the floor MUST be clamped with a diagnostic, not honoured, the same shape as R12's clamp. The key governs only the fast tier of [repo-discovery](../repo-discovery/requirements.md) R11's two-tier re-probe, the tier that revalidates against held ETags. The hourly tier for repositories without one is a constant this key never touches, which is what keeps every value of this setting affordable and is why the key exists at all: it is intent-level under R13's test ("how quickly should a newly active repository appear" is answerable from the person's own context, in minutes), where the scheduler's poll interval is not. [ADR-0020](../../adr/0020-discovery-scope-adoption-and-refresh.md) carries the reasoning.

**R21.** The Purge circuit breaker's threshold MUST be settable as `purge_breaker_failures`, MUST default to **50**, and MUST be clamped to the range **1 to 500**, an out-of-range value honoured at the nearer bound with a diagnostic, the same shape as R12's clamp. The upper bound is R12's inversion again: raising the threshold lowers protection, so the floor under protection is an upper bound on the value. The lower bound is 1, and there is no off value, because no configuration may produce a Purge whose breaker never fires, on the same grounds as R13's rejection of a stored setting that skips confirmation. The key is intent-level under R13's test: "how much sustained failure before my Purge gives up" is a trade a person can answer from their own context, their tolerance for an early stop against their tolerance for a grinding operation, where choosing a poll interval needs the points model they do not have. [purge](../purge/requirements.md) R21 owns the breaker's behaviour and what advances its counter. This key carries its numbers: the default, the floor and the ceiling live here and nowhere else.

**R22.** Every colour the interface paints MUST clear a stated contrast floor, per theme member. A **Role** (a foreground) MUST reach **4.5:1** against the background its member paints, measured by WCAG 2.x relative luminance. A **Highlight** (a foreground and background painted together) MUST reach the same 4.5:1 between its own two values, and its background MUST reach **CIE76 ΔE 10** against the background its member paints, so that the highlight is discernible at all. For `auto`, the only member that paints no background (R6), the measurement is against the **reference backgrounds** instead: **`#2d2a2e`** for the dark appearance and **`#faf4f2`** for the light one. A Role, a Highlight or a member added later MUST clear both floors, and the measured figures MUST be generated rather than recorded by hand.

**For a painted member the floor is exact, and for `auto` it is a stated assumption.** Both colours in a painted member are the tool's, so a ratio is arithmetic rather than a claim about somebody's terminal. `auto` inherits: the tool reads the terminal's background at startup and keeps only whether it is dark, on a split at HSL lightness 0.5, so the light appearance is painted on anything from white down to mid grey and no dark foreground clears 4.5:1 on `#808080`. Naming two real terminal themes rather than `#000000` and `#ffffff` is what makes that limb a worst case we commit to: contrast to a dark foreground rises monotonically as the background lightens, so clearing the floor on `#faf4f2` clears it on solarized-light, on `#fafafa` and on white. [ADR-0024](../../adr/0024-the-contrast-floor-and-its-reference-backgrounds.md), amended, carries the choice of standard, the values that moved, why a Highlight is a pair rather than two Roles, and why its reference backgrounds now bind `auto` alone. [ADR-0025](../../adr/0025-named-themes-and-who-owns-the-background.md) carries the members that paint.

**R22 is R16's other half, and neither substitutes for the other.** R16 requires that meaning survive colour being removed. R22 requires that colour be legible while it is there. R16 is why R22 can be a quality floor rather than a correctness one: nothing is unreadable at 3.80:1, because a text label carries the distinction either way. It is not why a floor is unnecessary, and an earlier reading that treated it that way is what left the tool painting 1.95:1 on a search match.

## Acceptance criteria

**AC1: No config file is a valid config.** With `$XDG_CONFIG_HOME` set to a temporary directory containing no config file, the tool starts, and every setting reports its default. Writing an empty `config.yml` changes nothing.

**AC2: State never enters the config file.** With `$XDG_CONFIG_HOME` set, no file is created under `~/.config/gh-runs/`. No ETag, repository list, or window state ever appears inside `config.yml`.

**AC3: Precedence holds.** A config file setting the default launch filter, overridden by the equivalent flag, yields the flag's value. With the flag absent it yields the config's value, and with both absent, the default.

**AC4: Exactly two keybinding profiles.** The keybinding profile accepts exactly `vim` and `standard`. Any other value, including `mac` or `windows`, is rejected with a diagnostic listing the two valid values.

**AC5: Exclusion reaches the network.** Excluding a repository removes it from the Feed and results in zero HTTP requests to it across a full polling cycle.

**AC6: The Budget knob is intent, not mechanism.** The Budget setting's schema admits no unit of time and no unit of requests. There is no config key, flag, or environment variable whose value is the scheduler's poll interval, a delete rate, a cache TTL, or a concurrency level (R13). `discovery_refresh_minutes` (R20) is not among these: it is the discovery revalidation interval, admitted by [ADR-0020](../../adr/0020-discovery-scope-adoption-and-refresh.md), and no other time-valued key exists.

**AC7: A rejected key gets its own reason.** Setting `poll_interval: 5` in `config.yml` starts normally and emits a diagnostic containing that key's reason from R13: that choosing it requires the token tier, repo count and points model. The same holds for the other four. Setting `some_future_key: 1` emits a generic unknown-key diagnostic and also starts normally.

**AC8: The confirm threshold is clamped.** With no config file the effective threshold is 50. Setting it to 5,000 clamps it to 500 and emits a diagnostic. Deleting a set of 500 then requires typing the count, and so does any cross-repository set at any size ([purge](../purge/requirements.md) R7). Setting it to 1 is honoured, because there is no lower bound. No config file and no environment variable produces a state in which a bulk deletion proceeds with no confirmation at all: in the TUI the modal still opens, and in the CLI `--yes` is still required on the command line.

**AC9: `NO_COLOR` beats the theme, and beats `CLICOLOR_FORCE`.** With `NO_COLOR` set to any value, including the empty string, `yes`, and `0`, R15a's resolver returns a profile no higher than `Ascii`, whatever the theme setting says. Rendering a frame through a `colorprofile.Writer` at that profile produces output carrying **no colour escape sequence** (no SGR 30 to 49, no 38/48 extended forms). The same holds with `CLICOLOR_FORCE=1` also set and the output piped, which is the case the library gets wrong.

**This criterion asserts no colour rather than no escapes, and the difference is deliberate.** `Ascii` keeps text decoration: a bold cell renders `\x1b[1m…\x1b[m`, measured. That is what no-color.org asks for ("prevents the addition of ANSI **color**"), what `colorprofile` documents ("will disable colors but not text decoration"), and what R15 says in its own words. Only the `NoTTY` profile strips every escape, and forcing it under `NO_COLOR` would suppress bold on a terminal that renders bold perfectly well, which no specification asks for and which helps nobody. An earlier form of this criterion demanded no ANSI escape sequences at all and was unsatisfiable against the pinned stack. It would have failed on bold, forever, while the accessibility property it exists to protect (R16, AC10) was never about bold.

**AC10: Meaning survives monochrome.** With colour stripped, every Status and Conclusion in the Feed remains distinguishable by text alone. As it happens, v1's `SKIP`/`GOOD`/`FAIL` labels already satisfied this.

**AC9 and AC10 cannot be goldens over `View().Content`, and [ADR-0013](../../adr/0013-dependency-pins.md) owns the reason.** lipgloss renders truecolour regardless of the environment, so the frame behind a `NO_COLOR` run is byte-identical to the frame behind a coloured one and a golden over it would pass without testing anything. Both criteria assert over the output of an explicit `colorprofile.Writer` instead. This is the only place in the suite where a colour profile appears.

**AC11: The view writes the file without damage.** Editing a setting in the TUI and quitting leaves `config.yml` changed in that key only, with unrelated comments and key order intact.

**AC12: Goldens hold the Settings view.** Rendering the Settings view from held state, with no terminal and no network, reproduces the stored golden byte for byte. The golden contains no row, label, field or help text for the scheduler's poll interval, deletes per second, a cache TTL, a concurrency level, or a stored setting that skips confirmation. Adding any of the five to the view fails it. The discovery refresh row (R20) is a different setting and does appear.

**AC13: The breaker threshold is clamped at both ends.** With no config file the effective breaker threshold is 50. Setting `purge_breaker_failures: 5000` clamps it to 500 with a diagnostic, and setting it to 0 clamps it to 1 with a diagnostic. No value, and no absence of one, produces a Purge whose breaker cannot fire ([purge](../purge/requirements.md) R21, and its AC13 pins the counting).

**AC14: Exclusion wins over a pin.** A repository named in both the exclude list and the pin list is excluded: it appears nowhere in the Feed and receives zero HTTP requests across a full polling cycle, exactly as an excluded-only repository does, and the pin has no observable effect.

**AC14 is testable now that R7's pin half ships** (issue [#97](https://github.com/jv-k/gh-runs/issues/97)). A repository named in both lists is excluded and receives no request across a full polling cycle, and the pin has no observable effect. The two settings meet at different layers rather than by a precedence rule: exclusion applies at discovery, so an excluded repository never enters the poll set, and a cadence tier is only ever chosen for a repository the poll set carries.

**AC15: Every colour clears the floor, and the figures are generated.** A test walks the palette's registry, every member and every entry, rather than the entries someone remembered to list, and asserts R22 over each: every Role at 4.5:1 or better against the background its member paints, every Highlight at 4.5:1 or better between its own two values, and every Highlight background at CIE76 ΔE 10 or more from that same background. For `auto` the background is R22's reference background for the appearance under test. Adding a Role, a Highlight or a **member** below either floor fails it, which is the whole of what bounds the theme set under R6. A golden holds the measured figure for every Role and every Highlight of every member, so the numbers this canon quotes are produced by the same arithmetic that enforces them.

**AC15 asserts over values, where AC9 and AC10 assert over rendered output, and that difference is why it needs no colour profile.** Those two need an explicit `colorprofile.Writer` because lipgloss renders truecolour regardless of the environment, so a golden over `View().Content` would prove nothing about colour. R22 is a property of the palette's values themselves, which no rendering path can change. It needs no profile, no frame and no view.

## Constraints

**The user has 163 repositories and cares about roughly 10** (~26 have Runs at all). That ratio is what makes R7 a real setting rather than a convenience: the difference between the discovered set and the interesting set is more than an order of magnitude, and no heuristic recovers the user's intent.

**Conditional requests are free** (a 304 consumes zero primary rate limit, verified by interleaved measurement), and ETag revalidation is simultaneously cheaper and more correct than any expiry policy. This is why cache TTL is not merely unnecessary but *meaningless*: every value a person could choose is strictly worse than the behaviour they already have.

**DELETE costs 5 points against a ~900 points/min secondary limit (~180/min), while GitHub's prose advises at least one second between writes (~60/min)**. That is a 3× disagreement, both figures documented rather than measured, and on an 18,258-Run Purge that published band is ~100 minutes versus ~5 hours. The governor reaches neither end: it caps at 150/min and floors at 30/min, so a real Purge runs ~2 hours to ~10 hours, and ~155 minutes with the Feed polling ([rate-governor](../rate-governor/requirements.md) R20). Any fixed rate is wrong for somebody: Enterprise Cloud has 3× the primary budget, GitHub Apps scale differently, and a token shared with CI has less headroom than the limit suggests. The adaptive governor observes what the account actually tolerates ([ADR-0007](../../adr/0007-adaptive-delete-throttle.md)). This is the whole argument for R8 and against R13's first two rows.

**A terminal erases the distinction that a third keybinding profile would encode.** On macOS, Cmd never reaches the application (Terminal.app and iTerm2 consume it for tabs and copy/paste), and Ctrl+C is SIGINT everywhere, so a "Windows" profile cannot map Ctrl+C to copy. Strip out what terminals actually deliver and "Mac keys" and "Windows keys" collapse into the same thing: arrows plus Ctrl. Shipping three profiles would cargo-cult a distinction that does not survive contact with the terminal (R5).

**`NO_COLOR` semantics are gh's, verified on gh 2.92.0** (`gh help environment`): "set to **any value** to avoid printing ANSI escape sequences for color output". Any value, not any non-empty value. R15 matches that reading deliberately.

**Three specifications disagree, and the pinned library is a fourth reading.** no-color.org says present and **not** an empty string. gh says **any** value. `colorprofile` v0.4.3 says whatever `strconv.ParseBool` accepts, which rejects `yes` and accepts `0` as false. Nothing reconciles these, so R15a picks gh's and resolves it in our own code rather than through detection. The measured table is in [ADR-0013](../../adr/0013-dependency-pins.md). **Note also that gh's own wording is loose in the same way AC9's was**: `Ascii` suppresses colour and keeps bold, so "avoid printing ANSI escape sequences" describes no implementation, gh's included.

**gh's config-directory precedent is verified**: `GH_CONFIG_DIR`, else `$XDG_CONFIG_HOME/gh`, else `$AppData/GitHub CLI` on Windows, else `$HOME/.config/gh`. R1 follows the XDG limb of it.

**Fine-grained PATs expose no scopes**, so no setting can be validated against the token's actual permissions ahead of time, and the API remains the final authority. A 403 can arrive despite `push: true`. A setting that gated on presumed permissions would be lying.

Historical note: v1's `SKIP`/`GOOD`/`FAIL` labels were derived by string-substituting the **Conclusion** field, and were plain text with no colour. That made them accidentally the accessible choice, and R16 carries the principle forward deliberately rather than by luck.

## Open questions

- **Resolved: the confirm threshold defaults to 50 and its hard maximum is 500.** The test this question set is the one the number meets. 500 sits three orders of magnitude below the reference repository's ~28,700 Runs, so the protection binds on every real Purge: the count gets typed whatever the config says, which is the intended outcome rather than a corner. 50 is roughly where a frozen set stops being reviewable by eye, so below it a `y`/`N` confirms rather than rubber-stamps. R12 carries both numbers, AC8 pins them, and [purge](../purge/requirements.md) R7, R8 and open question 1 own the reasoning.
- **Resolved: named tiers.** `budget: background | normal | greedy`, defaulting to `normal`. Ruled by the product owner on 2026-07-16, on the reasoning this question already carried: a percentage invites the same false confidence as a poll interval, and [rate-governor](../rate-governor/requirements.md) R8a rejects a compiled percentage on the grounds that no percentage is right for every account. R8's wording ("a share... and nothing else") already admits a named tier, since a tier names a share without numbering it. The tier-to-share mapping stays the governor's internal number, tunable without a config migration, and what each tier maps to is [rate-governor](../rate-governor/requirements.md) open question 3's to settle.
- **Resolved: the Budget share governs polling, and never a Purge.** The question assumed one allowance. There are two. The Budget is a share of the **primary** limit, which is observable and is what background polling spends. A Purge's throughput is bound by the **secondary** limit, a different pool with no counter to read. A Purge therefore does not saturate the Budget, and "spend 25% of my Budget" leaves a ~155-minute Purge at ~155 minutes rather than turning it into a multi-hour one. The knob's label stays honest, because it is a share of the thing polling actually spends. [ADR-0007](../../adr/0007-adaptive-delete-throttle.md) settles this on measurement and always did, so the earlier claim here that it does not address the interaction was wrong. [rate-governor](../rate-governor/requirements.md) R19 and AC14 are corrected to match.
- **Resolved: yes, honour all three (R15b).** `GH_ACCESSIBLE_COLORS`, `GH_ACCESSIBLE_PROMPTER` and `GH_SPINNER_DISABLED` are honoured on the same reasoning as R15's `NO_COLOR` trio: someone who configured these for gh is holding a gh extension, and accessibility is where honouring is the right default. [ADR-0008](../../adr/0008-full-cli-surface-despite-gh-overlap.md) commits to gh's flags rather than its config, which is why this is a decision, and the spinner limb is load-bearing rather than cosmetic given a Purge shows progress for ~155 minutes in the normal case and as long as ~10 hours at the throttle's floor. R15b now carries it.
- **Resolved: the trio is honoured as a set, and `NO_COLOR` wins outright.** R15a carries the order. This question was marked undecided while the pinned library had already answered it, and answered it against R15: `colorprofile` v0.4.3 lets a piped `CLICOLOR_FORCE=1` override `NO_COLOR` entirely, and ignores `CLICOLOR=0`, both measured ([ADR-0013](../../adr/0013-dependency-pins.md)). **A decision the library takes by default is still a decision, and leaving it open was choosing its answer.** Honouring the trio costs three lines in a resolver R15 already forces us to write, because R15's "any value" is unreachable through detection whatever we decide here. So the marginal cost of the other two is nothing, and the argument for them is the one this document already makes about `NO_COLOR`: someone who configured these for gh is holding a gh extension. [ADR-0008](../../adr/0008-full-cli-surface-despite-gh-overlap.md) commits us to gh's flags and not to gh's config, which is why this is a decision rather than an inheritance, but the trio travels together in gh, in bixense's specification, and in every other tool that reads them.
- **Resolved: there are no axes. It is a flat list of per-event options, living in the Settings menu.** [notifications](../notifications/requirements.md) R4 already ships that list, four events with their defaults, and R11 renders it as options. No events × scope grid and no events × Conclusion grid. A second axis would multiply four answerable questions into cells nobody can answer, which is the exact failure R11's intent test exists to prevent, and R4's events already carry their scope in their own wording ("a Run you triggered", "a repository you can push to"). Which cells the conservative default turns on was the other half of the question, and it is answered the same way: R4's table decides, and it is decided there already. This closes a circular deferral, where R4 shipped the table and this question called the axes undecided. Notifications defers to 2.1 ([PRD](../../PRD.md) Scope), so this resolution is preserved there and the flat list ships with the feature, not before it.
- **Resolved: as the structured Filter, not the CLI's `-s/--status` string (R9).** Reusing the CLI vocabulary would bake the permissive `-s/--status` conflation of Status and Conclusion into a stored default, which is a poor thing to persist. R9 now stores the default launch filter as [ADR-0016](../../adr/0016-the-filter-representation.md)'s structured Filter, with Status and Conclusion as distinct typed fields. The spelling is what the note under R19 makes the Runs tab's this-repo scope. The repository token both were waiting on is built (issue [#102](https://github.com/jv-k/gh-runs/issues/102)), so the scope is statable for a named repository, and `this-repo` as a `repos` entry states the working-directory one, resolved per launch by the Feed (issue [#117](https://github.com/jv-k/gh-runs/issues/117), [ADR-0016](../../adr/0016-the-filter-representation.md)). Both halves are decided, and the code each owes is tracked separately.
- **Resolved: yes, an "auto" member, and the floor is what bounds the set (R6).** The theme list was auto (derived from the terminal background, as gh does, and the default), dark and light, on the reasoning that a gallery is scope this view does not need. The bound has since been restated rather than lifted: issue [#152](https://github.com/jv-k/gh-runs/issues/152) asked for named themes, [ADR-0025](../../adr/0025-named-themes-and-who-owns-the-background.md) admits them, and what stops the set growing without bound is now R22's floor against the background each member paints, which AC15 enforces. That is a firmer line than "small and fixed" was, because a test holds it. R6 carries the set and the 2.1 timing, and `NO_COLOR` still overrides every member (R15).
- **Resolved: at startup, not watched (R17).** The config is read at launch, and the running view is the authority that writes its own changes back, so a hand-edit to `config.yml` is picked up at the next launch. Watching the file would race an external edit against the view's writes for a rare case, and is deferred. R17 now says so.
- **Resolved: absolute (R10).** R10 named the switch but no default. [live-run-feed](../live-run-feed/requirements.md) R4a settles it: it sizes the `run_started_at` column to the absolute instant `2026-07-15T16:39:00Z` as its reference rendering and calls the relative form "narrower, never wider", so absolute is the baseline the column is built around. Absolute is also the Feed's rendering today, so defaulting to it changes no existing frame and keeps every current Feed golden valid, with relative a pure opt-in that gains its own golden. The read-only CLI list defaults to a relative age column instead, each surface following its own canon: the CLI table carries no R4a width contract and mirrors gh's own list. R10 now carries the default.
- **Resolved: exclusion wins (R7, AC14).** A repository both excluded and pinned is excluded, removed from discovery, the Feed and all polling, with the pin having no effect. Exclusion is the stronger signal, and honouring the pin would poll a repository the person told the tool to leave alone, at a direct rate cost ([ADR-0003](../../adr/0003-multi-repo-via-client-side-fanout.md)). R7 now states the precedence and AC14 pins it.
- **Resolved: yes. 2.0.0 targets macOS, Linux and Windows** ([PRD](../../PRD.md), Scope, ruled 2026-07-16). R1 now carries the limb: `$AppData/gh-runs/config.yml` where `$XDG_CONFIG_HOME` is unset, mirroring gh's verified fallback. [local-store](../local-store/requirements.md) R22's lock gains its `LockFileEx` limb from the same ruling.
